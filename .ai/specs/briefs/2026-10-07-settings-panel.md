# Settings panel behind a navbar gear with /settings URLs and a phone-friendly channel table

- Date: 2026-10-07
- Category: feature
- Priority signal: medium — an ordinary feature; channel management works today, only its placement and phone layout are wrong
- Risk signal: medium — changes the shared `_Layout` (every page) and a protected route contract (`BACKWARD_COMPATIBILITY.md` §3); no schema or data change
- Routing: Next: om-auto-write-spec "Settings panel behind a navbar gear with /settings URLs and a phone-friendly channel table — brief: .ai/specs/briefs/2026-10-07-settings-panel.md"

## Problem

Channel management is configuration, but it sits in the primary navbar as a `Channels` link next to `News`. Every future configuration screen would add another top-level link. The owner wants one entry point, a gear icon, that opens a Settings area with categories, starting with Channels.

Two more requirements shape the design:
1. Every settings page lives under a `/settings/` URL prefix, so the channel pages leave `/RssChannels/*`.
2. The channel table must work on phones. Today, on a 390px phone, the Description, Added at and Actions columns overflow off-screen, and Fetch now, Edit and Delete can only be reached by horizontal scrolling.

## Agreed direction

Build the Settings panel as a full page with a category menu. Move channel management into it under `/settings/channels`, and make the channel table usable on phones.

Rejected options:
- **Offcanvas drawer or modal.** The channel CRUD forms are full, server-validated pages, and a drawer would need them rewritten as AJAX.
- **Categories stored in the database.** No setting values exist yet.
- **Redirects from the old URLs.** The owner rejected these knowingly, as a decision rather than to save effort.
- **Cards or sticky actions for the table.** The owner chose a slimmed table instead.
- **Building nothing.** This was offered, including deferring the table fix to a separate task. The owner chose to include the table fix in this feature as its own phase.

## Resolved unknowns

| Question | Answer (from the conversation) |
|----------|--------------------------------|
| Panel form | A full page with a left-hand category menu. Below the `md` breakpoint (<768px) the menu stacks above the content. |
| Entry point | A gear icon (`bi-gear`) replaces the `Channels` navbar link, aligned right. It needs an accessible name and a visible "Settings" label in the collapsed mobile menu, and is shown as active on every settings page. |
| How categories are defined | A static, ordered registry in code. Channels is first. No database, no per-user settings. |
| URL scheme | `/settings` redirects to the first category. Channel pages live at `/settings/channels`, `/settings/channels/create`, `/settings/channels/edit/{id}` and `/settings/channels/delete/{id}`. The Fetch now handler lives on `/settings/channels`. |
| URL casing | Lowercase. Links generated by the app must be lowercase too, so the spec must choose an explicit mechanism (e.g. `LowercaseUrls` or explicit `@page` routes) instead of relying on folder names. |
| Old `/RssChannels/*` URLs | Removed. They return 404 with no redirects, as a deliberate owner decision (self-hosted, single user, no external links). `BACKWARD_COMPATIBILITY.md` §3 is amended in the same PR: the new `/settings/channels*` routes and the Fetch now handler are listed as protected, and the removal of the old routes is recorded with its rationale. |
| Hardcoded links | Every `/RssChannels/...` link in views points to the new URLs, including the `/News` empty-state link (`Pages/News/Index.cshtml`). |
| Channel table below `md` | Hide the Description and Added at columns, and collapse the Fetch now, Edit and Delete buttons into one "⋯" dropdown menu. |
| Table acceptance criteria | At a 360px viewport the channels page has no horizontal scroll. The "⋯" dropdown opens fully and isn't clipped (the table currently sits in `.table-responsive`, an `overflow-x` container that clips dropdowns). Long channel names and URLs are truncated with an ellipsis. |
| Channel forms in the panel | Create, Edit and Delete take the full width of the panel's content column. Drop `col-md-8 offset-md-2`. |
| Phasing | Phase 1: the panel, the gear, `/settings` URLs and §3. Phase 2: the responsive table, with its own acceptance criteria, so it can be split into a separate PR if it fails QA. |

## Non-goals

- Storing setting values or any per-user preferences.
- Adding categories beyond Channels.
- A drawer, modal or navbar dropdown for settings.
- Redirects from `/RssChannels/*`.
- Translating the existing Polish validation messages in `CreateModel`. That's a separate issue.
- Changes to Domain, Application, Infrastructure, the worker or the database.

## Affected areas (if known)

- `src/Home.Scout.Web/Pages/Shared/_Layout.cshtml`: the navbar gear.
- The channel pages, currently `src/Home.Scout.Web/Pages/RssChannels/` (Index, Create, Edit, Delete). Their routes move under `/settings/channels`.
- `src/Home.Scout.Web/Pages/News/Index.cshtml`: the empty-state link.
- `BACKWARD_COMPATIBILITY.md` §3.
- A nested settings layout must re-render `@section Scripts`, because Create and Edit define it for client-side validation. Without it, Razor throws "section defined but not rendered".
